# DDAI Universal MCP Asset Catalog and Map Construction Design

## Status

Approved by the user on 2026-08-10. The user selected the local, client-agnostic MCP scope first; metadata plus bounded previews rather than original asset files; every Dungeondraft asset category; the hybrid live-catalog plus local-cache architecture; access to every loaded asset; and ingestion of assets generated by a connected AI model.

This design advances the unchanged product objective: a user connects an MCP-capable desktop AI client, describes a map in natural language, and the agent discovers the actual assets and supported operations available in the user's Dungeondraft installation, validates a structured plan, and constructs an editable native Dungeondraft map.

## Product boundary and success criteria

The connector is one standards-compliant local MCP server. Claude Desktop, ChatGPT Desktop, Gemini, Codex, and other compatible clients receive the same tools and schemas. Client-specific setup is limited to discovering and transactionally updating each client's MCP configuration; map behavior is not forked by client.

The feature is complete only when a published and installed connector can:

1. expose the same DDAI tool catalog through the official MCP protocol to each locally testable supported client;
2. obtain an authoritative snapshot of every loaded Dungeondraft asset category from the running DDAI mod;
3. retain a bounded local metadata and thumbnail cache that remains searchable while Dungeondraft is closed and clearly marks stale data;
4. return searchable asset metadata and bounded previews without revealing original asset files or local source paths;
5. inspect the live map and publish its current map and catalog revisions;
6. validate and apply revision-locked, idempotent native map plans that may use every supported Dungeondraft asset category;
7. fail closed on stale, missing, changed, disabled, or ambiguous asset references;
8. provide job-scoped undo, safe save, and user-directed export only through independently certified Dungeondraft APIs; and
9. accept a bounded image generated by a connected client, preserve it in a DDAI-owned user asset library, and make it available through the same catalog and placement contract; and
10. construct, save, reopen, inspect, and undo a representative multi-category native map in a live Dungeondraft 1.2.0.1 acceptance run without a new crash.

Passing unit tests, a fake bridge, or MCP tool discovery alone is not completion evidence.

## Authoritative Dungeondraft surface

Dungeondraft remains the source of truth for loaded assets and live map state.

- [`Script.GetAssetList(String category)`](https://megasploot.github.io/DungeondraftModdingAPI/Globals/) returns the loaded resource paths for a requested category from a tool script.
- The official [asset category list](https://megasploot.github.io/DungeondraftModdingAPI/AssetCategories/) defines Terrain, Patterns, Patterns Colorable, Caves, Roofs, Objects, Walls, Materials, Portals, Paths, Lights, Simple Tiles, Smart Tiles, and Smart Tiles Double.
- [`AssetPack`](https://megasploot.github.io/DungeondraftModdingAPI/reference/AssetPack/) exposes pack identity, version, author, keywords, preview, path, and `AllowThirdPartyUse` metadata.
- Dungeondraft calls a mod tool script after a map and its drawing assets have loaded, so catalog publication begins only after that lifecycle point. The connector does not infer a complete catalog from installation files.

Every mutating execution route must be separately certified against the exact supported Dungeondraft version. Filesystem scanning, private scene traversal, simulated mouse input, and direct `.dungeondraft_map` rewriting are not fallback mutation routes.

## Architecture

```text
Claude / ChatGPT / Gemini / Codex / another MCP client
                         |
                         | standard local MCP
                         v
                    ddai.exe
                   /        \
 catalog/preview/generated   atomic mailbox
        asset library
              ^                  |
              |                  v
              +-------- DDAI Dungeondraft mod
                              |
                              v
                 open native map + loaded assets
```

`ddai.exe` is the client-facing control plane. It owns MCP schemas and annotations, public validation, pagination, bounded image responses, cache integrity, request correlation, client setup adapters, and stable errors.

The DDAI GDScript mod is the Dungeondraft execution plane. It owns authoritative asset enumeration, live map inspection, runtime revalidation, native tool calls, mutation observation, and durable progress reporting through the existing atomic mailbox.

The cache is a performance and availability layer, never an authority for mutations. An agent may search a stale catalog while Dungeondraft is closed, but the result includes `live: false`, the source session, catalog revision, and snapshot time. Mutation requires a fresh bridge heartbeat and matching live revisions.

No inbound network listener is introduced. Each desktop client launches or connects to the local MCP process using a transport that the installed client officially supports. The first implementation preserves stdio as the common local transport and adds a client adapter only after that client's actual configuration and initialize/list/call behavior are verified.

## Catalog snapshots and stable asset references

After a map loads, and whenever enabled packs or loaded resources change, the mod builds a complete catalog snapshot. Enumeration is incremental across update ticks so thousands of assets do not freeze the Dungeondraft UI.

Each snapshot contains:

- schema version;
- bridge session ID and exact Dungeondraft/mod versions;
- snapshot timestamp and monotonically changing catalog revision;
- active pack metadata and relevant use-policy flags;
- category completeness and per-category counts;
- one record for every enumerated loaded asset; and
- generation errors or unsupported metadata fields without dropping otherwise valid records.

Each asset record contains an opaque `asset_ref`, category, display name, normalized search terms, tags and pack keywords where available, pack identity, preview availability, relevant dimensions or coloring capabilities where observable, and a non-secret resource fingerprint.

`asset_ref` is a versioned opaque identifier derived deterministically from normalized pack identity, category, and the Dungeondraft resource identity. It is not a filesystem path. A catalog revision change does not unnecessarily change references for unchanged resources, but mutation always resolves the reference through the current live catalog.

Catalog publication uses bounded, atomic, chunked files with a manifest containing record counts and hashes. `ddai.exe` accepts a snapshot only after the manifest, chunks, counts, hashes, schema, session, and category completeness validate. The previous valid snapshot remains available if a new snapshot is incomplete or corrupt.

## Preview generation and content boundaries

Original Dungeondraft assets, purchased pack files, and source paths remain local and are never returned by an MCP tool.

The mod derives a preview from the already loaded Dungeondraft texture, downsizes it to at most 256 by 256 pixels without upscaling, encodes it in a bounded supported format, and publishes it to the DDAI-owned cache under a content hash. Preview generation is incremental and deduplicated. A strict per-image byte cap, total cache cap, and least-recently-used cleanup prevent resource exhaustion.

Every asset actually loaded by Dungeondraft is searchable, previewable through a bounded derivative, and placeable through its opaque local reference. This includes built-in assets, purchased packs, user-created packs, and DDAI-generated assets. `AllowThirdPartyUse` and related pack fields remain visible as metadata and warnings, but do not hide an asset from the user's locally connected agent. The connector still never returns the original source file.

`ddai_get_asset_preview` accepts only a current or cached catalog-issued `asset_ref`. It returns a standard MCP image content block plus structured metadata. Clients that do not render MCP image content can still use the metadata. The server never accepts an arbitrary path, URL, or MIME payload as a preview request.

## AI-generated asset ingestion

`ddai_import_asset` turns an image supplied by a connected client into a user-owned asset under the DDAI application-data root. It accepts a declared category, name, tags, intended grid scale, optional coloring metadata, and either:

- bounded base64 image content in PNG, JPEG, or WebP form; or
- a one-time file token for an image already placed in the DDAI-owned import inbox.

It does not accept arbitrary filesystem paths or model-provided URLs. The server decodes into a bounded buffer, verifies the real format rather than trusting MIME text, rejects malformed or over-limit images, normalizes orientation and metadata, strips nonessential embedded metadata, hashes the content, and writes it transactionally to a DDAI-owned generated-asset library. Identical content is deduplicated without losing user-visible aliases or tags.

The import response returns a durable `generated_asset_id`, content hash, preview, and activation state. The connected agent can refer to that generated asset immediately in planning. Placement is permitted only after Dungeondraft has a persistent native route for the requested category:

- generated objects may use the documented [`ObjectTool.EmbebObject(String file)`](https://megasploot.github.io/DungeondraftModdingAPI/reference/ObjectTool/) route after exact-version live certification, producing a map-embedded native object; and
- categories that require a custom asset pack are assembled into a DDAI-owned generated pack and return `staged_reload_required` until Dungeondraft reloads and the live catalog confirms the resource.

The connector never assigns an in-memory texture and claims persistence without save/reopen proof. Once activated, generated assets receive ordinary `asset_ref` values, appear in `ddai_search_assets`, return previews, and participate in revision-locked plans exactly like other assets. Removing a generated asset requires an explicit DDAI-owned-library operation and is refused while known saved maps or active jobs still reference it.

## Public MCP contract

All compatible clients discover the same tools:

### `ddai_status`

Reports connector and bridge versions, Dungeondraft availability, map identity, heartbeat freshness, current map revision, current catalog revision, cache age, catalog completeness, and supported feature flags.

### `ddai_get_capabilities`

Returns the runtime-certified operation set, all asset categories, supported preview formats and limits, map/save/export capabilities, and any exact-version restrictions. It distinguishes schema support from live runtime certification.

### `ddai_inspect_map`

Returns a bounded structured description of canvas, grid, levels, native elements, placed asset references, and map revision. Large maps use deterministic pagination or region filters. Inspection never emits original asset data or secret local paths.

### `ddai_search_assets`

Searches the accepted cache by text, category, tags, pack, coloring capability, preview availability, and other cataloged fields. Results are deterministically ranked and paginated with a hard result cap. Every result identifies snapshot freshness and catalog revision.

### `ddai_get_asset_preview`

Returns one bounded preview and its non-secret metadata. It is read-only and subject to catalog-integrity and response-size limits.

### `ddai_import_asset`

Validates and stores one client-supplied generated image in the DDAI-owned asset library. It is state-changing but does not mutate the open map. The result reports whether the asset is immediately placeable, requires a Dungeondraft asset reload, or failed validation. An idempotency key prevents duplicate imports.

### `ddai_validate_plan`

Canonicalizes and validates a complete plan without changing the map. It validates schema, geometry, operation order, resource references, capabilities, limits, declared map/catalog base revisions, and every check possible outside the live mod. It lists checks that still require the live execution plane.

### `ddai_apply_plan`

Applies one canonical validated plan as an idempotent, revision-locked job. The caller supplies a unique request ID, expected map revision, and expected catalog revision. The bridge repeats all mutation-critical validation immediately before changing the map.

### `ddai_undo_last_job`

Reverses the connector's most recent completed job only when the job identity, current map revision, and certified Dungeondraft undo route prove it is safe. It never sends an unscoped generic undo into unknown user work.

### `ddai_save_map`

Saves only when the map already has a valid path selected by the user and the exact save route is live-certified. It never invents a path, overwrites another map, or automates a Save As dialog.

### `ddai_export_map`

Exports only to a user-approved DDAI export root, a supported format, and a collision-safe filename. The response reports the created artifact but does not expose arbitrary filesystem reads.

MCP annotations mark inspection, search, preview, capability, and validation tools read-only. Import is state-changing but does not modify the map. Apply, undo, save, and export are marked destructive or state-changing so compatible hosts can apply their normal confirmation policy.

## Universal map plan

The next schema version uses a typed `operations` array rather than adding unrelated top-level arrays. Each operation has an operation ID, type, level, geometry, style/options, and zero or more `asset_ref` values appropriate to its category.

The schema covers:

- terrain painting;
- normal and colorable patterns and floor regions;
- cave regions and cave edits;
- roofs;
- individual and scattered objects;
- walls;
- materials;
- portals and doors;
- paths;
- lights;
- simple tiles;
- smart tiles; and
- double smart tiles.

The schema also supports map and level creation/settings only where the live API is certified. Both installed and generated assets use the same `asset_ref` fields after activation. A plan may declare required `generated_asset_id` values, but validation fails until each has an active live reference. Unknown operation types, unsupported options, or operations absent from the current capability response are rejected rather than approximated through another tool.

Coordinates are explicit grid-relative or world-relative values with one declared coordinate system per plan. Geometry is bounded and overflow-safe. All units, rotations, colors, layers, sorting, lighting behavior, and asset references are explicit; the execution plane does not use cursor position or retained interactive UI state as hidden input.

Operations are ordered into deterministic dependency phases such as map/level setup, large surfaces, structures, portals, paths/materials, objects/tiles, and lights. The canonical plan records the resolved order so validation and execution agree.

## Mutation, revision, and undo model

Before execution, the bridge requires:

1. a fresh matching session and heartbeat;
2. the expected map identity and map revision;
3. the expected complete catalog revision;
4. every referenced asset to resolve to the same category and resource fingerprint;
5. every required Dungeondraft tool to exist and be runtime-certified;
6. relevant interactive tools to be idle; and
7. no other DDAI mutation job in progress.

The job is durably recorded before the first mutation. Each operation advances through prepared, applied-and-observed, and committed boundaries. Native tool calls must be followed by a category-specific observable postcondition; returning from a Dungeondraft method is not sufficient proof.

The bridge applies one job at a time. If an operation fails before any native change, the job fails cleanly. If one of several operations fails after earlier operations were observed, the bridge uses only a certified job-scoped reversal sequence. If complete reversal cannot be proven, it retains the journal and returns `mutation_outcome_unknown`; it never claims atomic rollback or automatically replays the plan.

A successful job increments the DDAI map revision and records the exact native changes needed to prove a later job-scoped undo. User edits outside DDAI invalidate that undo guarantee when they can be detected; otherwise the connector fails closed rather than risking undoing user work.

Repeated identical request IDs return the existing correlated result. Reusing an ID with different canonical content is a conflict. Timeouts remain unknown outcomes and do not recommend retrying under a new ID.

## Client setup and discovery

Setup uses a small adapter per supported desktop client. Each adapter:

- locates only documented or live-verified per-user configuration;
- preflights and parses the entire existing configuration;
- proves ownership before replacing or removing an existing `ddai` entry;
- makes a timestamped sibling backup before the first mutation;
- changes only the DDAI-owned entry;
- preserves unrelated servers and formatting-compatible data;
- writes transactionally and validates the result; and
- can restore or uninstall only what DDAI owns.

The connector is not advertised as working with a client until a published installed build completes MCP initialize, tools/list, at least one read-only tool call, image-content handling or its documented fallback, and one approved mutation round trip through that client. Where a client accepts standard MCP but uses a different transport or packaging format, the adapter changes; the server contract does not.

## Error handling and limits

All expected failures use stable machine-readable codes plus concise remediation. Public responses never include raw exception dumps, original asset paths, client secrets, or unrelated configuration contents. Catalog display names remain available because they are required for asset search and selection.

Important failures include:

- `dungeondraft_not_running`;
- `bridge_not_ready`;
- `catalog_unavailable`;
- `catalog_incomplete`;
- `catalog_stale`;
- `catalog_revision_conflict`;
- `map_revision_conflict`;
- `asset_not_found`;
- `asset_changed`;
- `asset_category_mismatch`;
- `preview_not_available`;
- `invalid_generated_asset`;
- `generated_asset_too_large`;
- `generated_asset_not_active`;
- `generated_asset_reload_required`;
- `unsupported_operation`;
- `tool_busy`;
- `mutation_outcome_unknown`;
- `undo_not_safe`;
- `save_path_required`; and
- `export_not_permitted`.

Mailbox requests and responses retain the existing 1 MiB caps. Generated-image transfer does not use the mailbox; it uses a separately bounded local MCP import path and DDAI-owned inbox. Catalog chunks, search queries, result counts, pagination cursors, plan operation counts, geometry point counts, preview dimensions, preview bytes, generated-image decoded dimensions and bytes, cache size, processing time per Dungeondraft frame, and total job duration all receive explicit limits. Invalid or oversized input is rejected before allocation or mutation.

## Testing strategy

Implementation follows red-green TDD and preserves every existing status, mailbox, installer, MCP, timestamp, and rectangular-wall test.

Offline evidence must cover:

- deterministic stable references for unchanged resources and changed references/fingerprints when identity changes;
- all official asset categories and completeness accounting;
- chunked snapshot publication, validation, interrupted publication, corruption, recovery, and retention of the last valid snapshot;
- bounded preview generation, dimensions, encoding, hashes, deduplication, cache eviction, all-loaded-asset coverage, and absence of original paths/bytes;
- generated-image import through both bounded input forms; content sniffing; metadata stripping; decompression-bomb and malformed-image rejection; deduplication; transactional writes; idempotency; DDAI-root confinement; activation and reload states; and saved-map reference protection;
- paginated search, filters, ranking stability, stale labeling, and strict caps;
- MCP structured content and image content through the official SDK, including a metadata-only client fallback;
- universal plan serialization and validation for every category and mixed plans;
- map/catalog revision conflicts, missing assets, changed assets, category mismatches, busy tools, and unsupported runtime capabilities;
- one-at-a-time mutation execution, durable transitions, duplicate idempotency, conflict rejection, crash recovery at every boundary, and ambiguous-outcome non-replay;
- job-scoped undo safety and refusal after an intervening edit;
- save/export path and ownership boundaries;
- transactional client setup, foreign-entry preservation, idempotence, rollback, and uninstall ownership for every adapter;
- a published executable completing MCP initialize/list/search/preview/validate/apply through the official SDK;
- exact-version GDScript parser and static contract checks;
- the complete Release test suite and build with zero failures, warnings, or errors; and
- sensitive-data and executable-listener scans.

Static GDScript token checks cannot prove runtime behavior. Each category-specific executor requires a read-only or disposable-map certification against Dungeondraft 1.2.0.1 before it is advertised by `ddai_get_capabilities`.

## Live acceptance

Live acceptance uses a new disposable map and DDAI as the sole required active mod. The user controls normal Dungeondraft close/reopen and any save-path selection; DDAI does not terminate the process or automate unsaved-work dialogs.

The acceptance run must:

1. establish a fresh heartbeat, map identity, revisions, and pre-run crash-event baseline;
2. enumerate all official categories and reconcile catalog counts with the live mod;
3. use an official MCP client to search every loaded asset and render multiple bounded previews without disclosing source paths;
4. import a newly AI-generated image, activate it through the certified native route, and prove it appears in search and preview results;
5. validate and apply a representative plan containing every runtime-certified category plus the generated asset;
6. visually inspect the native map and programmatically inspect the resulting map state;
7. prove stale-catalog and changed-asset rejection on a disposable case;
8. prove one job-scoped undo removes exactly that job and not earlier/user work;
9. reapply with a fresh request, save to a user-selected path, close, reopen, and prove native and generated-asset persistence;
10. export to the approved DDAI export root and verify the artifact;
11. verify that Dungeondraft remains responsive with a fresh heartbeat and no new crash dump or Application Error event; and
12. repeat MCP initialize/list/search/preview/import/status with each locally installed supported client adapter, including ChatGPT Desktop when its local MCP configuration is available.

Any category without an exact-version certified native operation remains present in the catalog but is reported as non-mutable in capabilities until certification succeeds. The overall goal is not complete until every category required by this design is certified or a documented Dungeondraft API limitation is presented to and explicitly accepted by the user.

## Delivery sequence

The implementation plan may stage work internally to keep failures diagnosable, but it may not redefine success around an easier subset. The intended order is:

1. versioned catalog and cache contracts;
2. live all-category enumeration and bounded previews;
3. generated-asset ingestion, DDAI-owned storage, and native activation;
4. MCP search, preview, import, capabilities, and inspection;
5. universal plan schema and validators;
6. exact-version category executor certifications and implementations;
7. revision-locked mixed-plan application and job-scoped undo;
8. safe save/export;
9. client adapters and published-build compatibility proofs; and
10. full live multi-category acceptance.

The existing rectangular-wall operation remains supported throughout migration and becomes one operation in the universal plan rather than a discarded special case.
